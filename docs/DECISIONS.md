## D-017 – Implementation choices in batch A (2026-09-29)
Interpretations of the design made while building P1-1 … P1-4; each has a test.
- **PEP-1 scope:** G1 permits the four read tools for any valid token; G2 permits the four write tools only for a real user (`username`) with scope `fairtable/book`; G3 (`party_size > 10`) applies to **every** tool (`party_size` is 0 where a tool has none); G4 (`has`-guard, verified agent) applies to the **write** tools only, so reads stay open to bots as G1 says.
- **Fail closed:** any Cedar evaluation error, or a reason the loader does not know, is a deny (`policy_error`); no matching permit is a deny (`no_permit`, reported as the permit that was missing: G2 for PEP-1, P0 for PEP-2). `PolicyContext` (PEP-2 facts) has no defaults: a missing fact is a bug, not a pass.
- **Startup validation:** each policy bundle is validated against a local Cedar schema (`policies/pep1.cedarschema`, `pep2.cedarschema`) and must have `@id`; forbids need `@on_deny` (`deny` | `step_up`); any problem stops the server. Typos in attribute names are caught at load time.
- **Extra error codes** beyond the design's list: `UNAUTHENTICATED`, `INVALID_SLOT_TOKEN`, `SLOT_TOKEN_EXPIRED`, `CONSENT_DECLINED`. Every code has a default `next_step`. Internal reasons (why a token was rejected, Cedar error text) stay server-side.
- **Slot token:** HMAC-SHA256, **bound to the user's `sub`**, default lifetime 15 minutes, secret at least 32 bytes from config. Only `Identity` is a domain model so far; venue, slot and hold models arrive with the store (P1-6).
- **Verifier:** RS256 only by default; `audience_claim` is configurable (`aud`; `client_id` for Cognito-style access tokens, to be checked on real Cognito in Phase 2, scaffold-only until then). JWKS over HTTP is cached 10 minutes, a forced refresh (unknown `kid`) is throttled to once per 30 s, stale keys are served during an outage; an outage with a cold cache raises `JwksUnavailable`, which is not a token error and is masked and denied by the tools layer.

## D-019 – Implementation choices in batch B (2026-09-29)
- **Dev issuer:** agent claims come from the OAuth **client**, not the user (as in the design's pre-token trigger). Clients: `alexa-plus-sim` (verified; password grant for diners, and V3-style machine tokens with the claims), `shady-agent` (unverified), `bot-m2m` (no claims). Owners carry `cognito:groups=["owners"]`. Passwords and secrets are public dev values listed in the README.
- **Storage:** one table with two overloaded indexes (`GSI1`: venue directory now, hold-expiry later; `GSI2`: a user's holds and reservations later). Ids that enter keys reject `#` and control characters. `Slot.held_until` is checked on read (lazy expiry, D4). Times in slots are wall-clock times compared with the server clock's date and time. **Decided by the developer: keep it simple, use the server's time zone (UTC by default, from the injected clock); no per-venue time zone.**
- **Rate limit:** only `availability_check`, per (user, restaurant), a token bucket of 20 per hour (configurable), optimistic update; on repeated self-contention the request is refused (fail closed).
- **`mandate_status` without a mandate** returns a normal answer (`mandate_state: none`, "every booking will need approval") instead of the design table's `NOT_FOUND` + `consent_url`. `NOT_FOUND` is kept for an unknown restaurant. Reason: a missing mandate is a normal state, and the create-mandate page is only a "Should". **Confirmed: the developer left this to my judgement and it stands.**
- **Write pipeline (`server/pipeline.py`):** PEP-1 → idempotency lookup → facts → PEP-2 → one transaction (tool writes + idempotency record + audit). Idempotency key is 8-128 characters `[A-Za-z0-9._:-]`; the stored-result replay carries `idempotent_replay: true`; the hash covers the tool name, so one key cannot be reused across tools. Denials, step-ups and failures store no key (the same key can be retried after the cause is fixed) but are audited with a separate best-effort write. A duplicate delivery that lands between lookup and write is detected by the idempotency condition inside the transaction.
- **Error boundary:** tools raise `FairTableError`; `@business_errors` turns it into a `BusinessError` (a `ToolError` at INFO level, so FastMCP logs no traceback for routine refusals) and `ErrorMappingMiddleware` returns the structured `isError` result. Real bugs stay masked and loud.
- **Server defaults:** Origin/Host protection on, `mask_error_details=True`, bind `127.0.0.1` unless configured; the profile `aws` refuses the built-in dev slot-token secret.

## D-020 – Design of the booking flow, batch C (2026-09-29)
Settled before coding P1-9 … P1-13 (research: mcp 1.30 / FastMCP 3.4.7 source, MCP spec 2025-11-25).
- **Records.** *Hold* (`HOLD#id`): user, agent, venue, date, slot, party, status `held|confirmed|released|expired`, `held_until` (10 min, `HOLD_TTL_S`), terms snapshot; while `held` it is listed in GSI1 (`HOLDS#venue#date`, sorted by expiry) and GSI2 (`USER#sub`). *Reservation* (`RES#id`): confirmed booking with code, terms snapshot, status `confirmed|cancelled`. *Approval* (`APPROVAL#subject_id`): what the user must approve (`confirm` a hold, or `cancel_fee` on a reservation), the user's `sub`, a hash of the terms, status `pending|approved|declined|used`, valid 15 minutes, single use. The subject id is a random 128-bit id, so the consent URL is `{CONSENT_BASE_URL}/consent/{subject_id}`; it grants nothing by itself, the page requires a login as the same `sub`.
- **Counters.** S1 counts a user's *held* holds per restaurant (max 2, equal to the Cedar rule; a test keeps the two in sync). S2 counts agent covers per restaurant and day (holds + reservations). Confirm lowers S1 only; cancel lowers S2; expiry lowers both.
- **Lazy expiry (D4).** Before a hold or confirm, expired holds of the restaurant/day (GSI1) and of the user (GSI2) are released, one small transaction each (hold to `expired`, both counters down). The slot itself is treated as open once `held_until` has passed (read side and write condition), and is restored best-effort. No worker.
- **Step-up (D-016).** A `STEP_UP` decision becomes: (1) if the client declared `elicitation.url`, JSON-RPC -32042 with the consent URL; (2) otherwise an `isError` result with `consent_url` and code `CONSENT_REQUIRED` (confirm) or `FEE_APPLIES` (cancel). Both create the approval once (a repeat call reuses it) and put a message in the *dev inbox* (a `Notifier` seam; item `INBOX#sub` in DynamoDB, shown by the chat page later; SNS is a later option). The SDK's `check_client_capability` only tests that `elicitation` exists, so the tool reads `client_params.capabilities.elicitation.url` itself; no session (stateless) means rung 2.
- **Approvals.** The agent retries with the same `idempotency_key`; an approved, unexpired, unused approval for the same terms hash makes the Cedar fact `mandate_covers_booking` / `cancel_fee_acknowledged` true and is consumed in the same transaction. A declined approval gives `CONSENT_DECLINED`.
- **Cancel fee.** A flat venue fee applies when the booking starts within `free_cancel_hours` (server time zone). The design's diagram says "per person"; flat is the MVP simplification.
- **`reservation_manage`.** `view` changes nothing and skips the pipeline (PEP-1 and ownership only). `cancel` runs the pipeline (S3b applies). `modify` is limited to **reducing** the party size (never adds covers or cost); an increase is refused with a hint to cancel and rebook. Cancel frees the slot and is where waitlist matching hooks in later (P1-14).
- **Consent page (`web/`).** Cookie session signed with HMAC (no extra dependencies), login through the dev issuer, CSRF token on the decision form, `X-Frame-Options: DENY`, strict CSP, `Cache-Control: no-store`.
- **Invariants.** `server/invariants.py` checks I1 (no booking outside mandate without an approval), I2 (no double-booked slot), I3 (a fee is only charged with an approved approval), I5 (no write without identity) plus counter consistency; used by the concurrency tests now and by the eval graders later. I4 (one ticket per drop) arrives with Fair Drop.

## D-022 – The hold is lengthened once for a step-up approval (2026-09-29)
- **Problem found in review:** a hold lasts 10 minutes but a phone approval is valid for 15, and an approval is only useful while the hold is alive. A user who took 11 minutes lost the table although they did everything right, and the consent page said "no longer active".
- **Decision (developer chose option A):** when a *confirm* needs approval, the hold is lengthened **once**, to the end of the approval window (15 minutes from the first ask), together with the slot, in one guarded transaction (`lifecycle.extend_hold`). Holds that do not need approval stay at 10 minutes. The lock is bounded: the step-up can only start while the hold is alive (at most 10 minutes after it was taken) and adds at most 15, so a table is never locked longer than about 25 minutes, and only when the user was actually asked. It cannot be extended twice, after expiry, or after the slot was taken over.
- **Messages:** the -32042 prompt and the `consent_url` hint now say how many minutes the user has.
- **Not chosen:** one longer TTL for every hold (locks tables needlessly), a longer TTL only for holds known to be outside the mandate (less exact), and re-taking the table automatically after approval (surprising).
- **Login on the consent page (explained to the developer):** the link is in the assistant's hands, so approving must need something the assistant does not have: a sign-in through the dev issuer (Cognito hosted login on AWS, scaffold). Task P1-19 will serve the chat page and the consent page from the same web app so one sign-in covers both; the session length (now 1 hour) is still open.

## D-023 – Design of waitlists and Fair Drop, batch D (2026-09-29)
No internet research was needed: SHA-256, HMAC-SHA256 and commit-reveal are standard-library operations; MCP Tasks stay off (D-010); KMS is scaffold only (D-016). Design read from `fairtable-solution-design.md` sections 7.2, 7.3 and the plan tasks P1-14 to P1-16.
- **Standing watch (`waitlist_watch`).** A *watch* records who wants a table (restaurant, date, time window, party size) plus a snapshot of the caller's verified identity (`sub`, `username`, `agent_tier`, `agent_id`, scopes). **One active watch per person per restaurant per day** (`ALREADY_ENTERED` otherwise; the watch ends on match, cancel or expiry and then a new one is allowed). If a fitting table is free right now the tool says so and creates nothing. A watch consumes no covers (D1); it needs a verified agent (P0) like every write.
- **Matching is lazy.** When a table is freed (a cancel, or an expired hold released by the lazy sweep) the freed slot is offered to waiting watchers in arrival order (FIFO by creation time). The matcher takes the first watcher whose window and party fit and creates a normal 10-minute hold for them through the same write pipeline with the stored identity snapshot, so S1, S2 and P0 still apply (a denied watcher is skipped). The hold and the watch's change to `matched` are one transaction, so two matchers cannot both win. The watcher is told in the dev inbox and finds the hold with `waitlist_status`; confirming is the normal `reservation_confirm`. Drop-controlled slots are never matched by a standing watch.
- **`waitlist_status`** (read tool) takes a `watch_id` (a watch or a drop entry) and `action` status | cancel. It answers `waiting` with `retry_after_s` and a next step, `matched` with the hold and its expiry, `expired`, `cancelled`; for drop entries `entered`, `won`, `lost`, `skipped`. Cancel is a single conditional update by the owner (no idempotency key needed, repeating it is harmless).
- **Fair Drop.** A *drop* covers one or more drop-controlled slots (`drop_id` on the slot) and has `opens_at`, `drop_at`, capacity = number of its slots, and a **commitment** = SHA-256 of a secret 32-byte seed, published from the start (in the entry answer, `waitlist_status` and the audit resource). The seed comes from a `SeedProvider` (`secrets.token_bytes` locally; a KMS `GenerateRandom` implementation exists as scaffold only and is not called). Entries: `waitlist_watch(drop_id=...)`, **one per verified person per drop** (a conditional write on `ENTRY#hash`, RT12), only while `opens_at <= now < drop_at` (`DROP_CLOSED` after). The entry id is `drop_id~SHA-256(drop_id|sub)` so the public audit never shows a `sub`.
- **Allocation (lazy, exactly once).** The first request after `drop_at` (a `waitlist_watch` on the drop, a `waitlist_status`, or a read of the audit resource) claims the drop with a conditional status change `open -> allocating` (a stale claim older than 60 s can be taken over), orders the entries by **HMAC-SHA256(seed, entry_id)** ascending, and walks down the list giving each entry a hold on the next free drop slot that seats the party, through the pipeline with the winner's stored identity. This is the one sanctioned route around rule S4 (the win is the authorisation), so the operation passes `slot_is_drop_controlled = false`; S1 and S2 still apply and an entry that cannot take a hold is `skipped` with the rule id and the walk continues. Idempotency keys `drop-<id>-<entry hash>` make a resumed run safe. Winners confirm through the normal flow (mandate or step-up). Finally the drop becomes `allocated`, the seed is revealed and the audit is stored.
- **Audit** (`fairtable://drops/{drop_id}/audit`, public): before allocation the commitment and the rules; afterwards the seed, every entry id in entry order, the HMAC order, the winners and skipped entries. `verify_audit()` recomputes commitment, order and winners from the published data alone, so anyone can check the draw.
- **Resources** `fairtable://restaurants/{id}/policies` (rules in plain English plus the restaurant's caps) and the audit above need no sign-in: they hold no personal data.
- **Invariants.** I4 (one ticket per person per drop) joins `server/invariants.py`; counters and slots stay consistent through watch matches and allocation.

## D-024 – What batch D changed or found (2026-09-29)
- **Race fixed in the write pipeline (found by the concurrency tests).** A duplicate delivery could pass the first idempotency lookup, the original could then commit, and the copy would fail its own checks for a reason the original had just created ("slot taken", "hold no longer active") instead of returning the stored result. Every failure after the first lookup (facts, rule refusal, step-up, plan, transaction) now looks the key up once more and returns the stored result (or `IDEMPOTENCY_CONFLICT` if the parameters differ). It appeared about once in five runs of the 20-simultaneous-confirms test; eight consecutive runs are clean and three deterministic tests cover the window.
- **Watches and tickets:** one shared `watch_id` argument; a Fair Drop ticket id is `drop_id~SHA-256(drop_id|sub)`. Withdrawing a ticket before the draw deletes it (re-entering gives the same id, so nothing can be gained). `waitlist_status` is annotated as not read-only because it can cancel; its access rule is still G1.
- **Draw time in the seed data:** entries open at seed time, the draw is 24 hours before the seats and never sooner than 10 minutes after seeding, so a fresh demo can always enter first.
- **Public resources need no sign-in** (`fairtable://restaurants/{id}/policies`, `fairtable://drops/{id}/audit`); reading the audit after the draw time runs the draw, like any other first request.
- **`KmsSeedProvider` exists as scaffold only** (D-016): it is tested against a fake client and never called against AWS.

## D-027 – What A0 and A2 mean in the evaluation (2026-09-30)

## D-032 – How the server emits traces (2026-09-30)
Built for the server part of plan task P2-9; nothing here touches AWS. Verified on the installed packages (`opentelemetry-api`/`-sdk` 1.45.0, `fastmcp` 3.4.7, `mcp` 1.30.0), see `docs/PLAN.md` section 3a.
- **One span per tool call**, `fairtable.tool <name>`, opened by `TelemetryMiddleware` (server/telemetry.py). It is added first, so it is outermost and sees the final result after `ErrorMappingMiddleware` has turned refusals into `isError` results. It never changes what the caller receives.
- **Attributes are an allow-list** (`ALLOWED` in `server/telemetry.py`): tool, caller kind (`user` / `machine`) and agent tier, restaurant id, party size, each policy layer's decision and rule ids (`pep1.*`, `pep2.*`), outcome (`ok` / `refused` / `step_up` / `error`), error code, rule id, idempotent replay, and the exception class name on a bug. A name off the list raises, so a mistake shows in tests. Never present: token, slot token, user id, username, idempotency key, hold or approval id, approval link, free text, exception messages. A test runs a whole booking with a step-up and scans every span for these.
- **Outcome vs status.** A refusal or an approval request is an ordinary result, so its span is *not* marked as an error; only a bug (an unexpected exception) sets status `ERROR`, with the class name and no message.
- **Why a context variable.** FastMCP opens its own inner span; with only our provider configured that inner span does not record, so "the current span" inside the tool is useless. `annotate` writes to the tool span kept in a context variable, which reaches the tool's worker thread.
- **Joining the caller's trace.** A Strands agent puts its trace context in the request's `_meta`. FastMCP hands it to the server on `fastmcp_context.request_context.meta` (not on the call's params, which arrive with `meta=None`); the span is parented on it, so agent, Gateway and server steps form one trace.
- **No SDK, no cost.** Without an OpenTelemetry SDK the API is a no-op. The server never configures a provider or exporter: on AWS the AWS Distro for OpenTelemetry (or Runtime's instrumentation) does (P2-9, later). Tests inject an in-memory provider with `use_tracer_provider`.

## D-036 – First contact with real DynamoDB: retries with jitter, `TEMPORARILY_BUSY`, and the CDK layout (2026-09-30)
Found by running the store race on the real table (P2-1); the local DynamoDB never showed it (it serialises transactions).
- **Finding.** 30 rounds of 20 simultaneous transactions on one slot: always exactly one winner (the guarantee holds), but 16 of 600 requests ended in `StoreBusy` (a transaction cancelled by `TransactionConflict` four times in a row), and nothing in `server/` handled `StoreBusy`, so a diner would have got a masked internal error.
- **Fix.** `Store.transact` now makes up to 8 attempts with full-jitter exponential backoff (cap 0.4 s; AWS Architecture Blog, "Exponential Backoff And Jitter"). What is left reaches the agent as the new error code **`TEMPORARILY_BUSY`** (`retry_after_s: 1`, next step: repeat the same call with the same `idempotency_key`; safe because nothing was written). Re-measured on the real table: 0 of 600. The code is added to the list in D-017.
- **CDK layout.** `infra/cdk/` holds a Python CDK app (`aws-cdk-lib==2.271.0`, `constructs==10.8.1` in a git-ignored `.venv`) and the CLI pinned in `package.json` (`aws-cdk@2.1143.0`, run with `npx cdk`). Two stacks: `FairTableData` (the table, same keys as `server/store/table.py`, on-demand, AWS-owned encryption key, destroyed with the stack) and `FairTableBudget` (created only when `BUDGET_EMAIL` is set). Account and region come from the CLI credentials, the table name from `TABLE_NAME`.
- **Budget.** One cost budget `fairtable-150usd` with actual-spend alerts at $50, $100 and $140, **credits excluded** (`IncludeCredit` defaults to true, which keeps the measured spend near zero while the credit lasts, so the alerts would stay silent). ## D-046 – Gateway design (P2-5, built, not deployed; 2026-10-01)
Researched in the AWS documentation (list in `docs/PLAN.md` section 3a-bis); nothing here has run on the account yet.
- **Shape.** Stack `FairTableGateway`: Gateway `fairtable-gw` (MCP, version 2025-11-25 only), inbound `CUSTOM_JWT` on the Cognito pool (discovery URL of the pool, **allowed clients = the three app clients, no allowed audience**: Cognito access tokens carry `client_id`, not `aud`), one target `ft` (an MCP server target whose endpoint is the Runtime's URL-encoded invocation URL, listing mode DEFAULT), outbound **IAM SigV4** with the gateway's own role (`iamCredentialProvider`, service `bedrock-agentcore`), one REQUEST interceptor with `passRequestHeaders: true`.
- **The interceptor** (`infra/gateway/interceptor/handler.py`, standard library only) copies the verified bearer token into `x-ft-user-token` and returns that header and nothing else. It never sends `Authorization` on: an interceptor's `Authorization` is forwarded to the target and would clash with the gateway's own signature. A header the client forged under the same name is replaced (interceptor headers take precedence). With no usable bearer token it answers 401 itself and forwards nothing (fail closed), so a forged header alone never gets through. It never logs headers (the documentation warns that they carry tokens); tested.
- **One name in three places.** `x-ft-user-token` is the interceptor's output, the target's `allowedRequestHeaders` and the Runtime's `requestHeaderAllowlist`; a test fails if they drift apart.
- **The gateway role** is assumed only by `bedrock-agentcore.amazonaws.com` for gateways named `fairtable-gw-*` of this account, and may only: `bedrock-agentcore:InvokeAgentRuntime` on the runtime and its endpoints (the action and resource types are from the machine-readable service reference; the Gateway page does not name them), `bedrock-agentcore:InvokeGateway` on this gateway (the page asks for it; a permission-management action), and `lambda:InvokeFunction` on the interceptor only.
- **Tool names.** The Gateway names tools `<target>___<tool>`; the target is called `ft`, so `ft___restaurant_search`. Consequences handled in P2-10: the simulator maps the prefix (its scripted model and the steps list), and the tool descriptions and `next_step.tool` keep the bare names (an assistant can match them by suffix; the Gateway offers no switch to drop the prefix).
- **Not decided here.** Gateway Policy (P2-6), whether `-32042` passes through (P2-7; elicitation needs sessions and streaming on the gateway, off for now), observability (P2-9).
- **Cost** (AgentCore pricing page, read raw on 2026-09-30): $0.005 per 1,000 tool invocations, no charge for the interceptor beyond Lambda (free tier), no semantic search or indexing configured.

## D-047 – Cognito sign-in for the web pages, and the assistant through the Gateway (P2-10, 2026-10-01)
- **Sign-in.** `CognitoLogin` (`web/auth.py`) signs people in with Cognito's `InitiateAuth`, flow `USER_PASSWORD_AUTH`, as the app client `alexa-plus-sim` (the one whose tokens carry the agent claims the chat needs). `SECRET_HASH` (base64 of HMAC-SHA256 with the client secret over username plus client id) is added because that client has a secret. The Cognito client is created **unsigned** (`InitiateAuth` is an unauthenticated operation: the password is the credential), so the pages need no AWS credentials. The access token that comes back goes through the same verifier as the server's (issuer, all client ids, `client_id`, `token_use=access`); a refusal, a challenge, a machine token (no username), an ID token or a network failure is simply "not signed in". Neither the password nor the client secret is logged. The same sign-in covers the consent page, the owner console and the chat.
- **Settings.** `AUTH_PROVIDER=dev|cognito` (default `dev`), `COGNITO_CLIENT_ID`, `COGNITO_REGION` (default `AWS_REGION`); the client **secret** is read from `COGNITO_CLIENT_SECRET` where the login is built and is not part of `Settings` (so settings can be logged). `MCP_VIA_GATEWAY=true` makes the chat's assistant send `Authorization: Bearer <token>` to `MCP_URL` (the Gateway) instead of `x-ft-user-token` to the server, and turns on the tool-name prefix `ft___` (`MCP_TOOL_PREFIX` overrides; never used on the direct route).
- **The prefix.** The Gateway names tools `ft___<tool>`. The scripted model calls the prefixed names, and `transcript()` strips the prefix, so personas, the steps list and the eval graders keep seeing the server's own names. A real model sees the prefixed names from the tool list.
- **Local profile unchanged:** every default keeps the dev issuer and the direct route.
- **Measured on the real account** (second account, `tests/aws/test_demo_flow.py`, 4 of 4): Cognito sign-in through the pages; a booking inside Alice's permission by chatting through the Gateway; Bob's booking outside his permission: the assistant hands over a consent link (the step-up reaches the diner as an ordinary result with `consent_url` through the Gateway), Bob approves on the consent page with the same sign-in and the booking completes; a wrong password does not sign in; the owner console works with a Cognito owner token. What the test booked was cancelled (7 cancelled, none left confirmed or held).

## D-048 – `-32042` does not survive the AgentCore Gateway; on AWS the step-up uses the plain result (P2-7, 2026-10-01)
- **Question (P2-7).** Does a JSON-RPC `-32042` (URL elicitation required) from the server reach the client through the Gateway?
- **Measured on the real account**, with a FastMCP client that declares URL elicitation, a diner without a permission (Bob, Carol), `reservation_confirm`:
  1. *Runtime stateless (the deployed default), Gateway without sessions:* the server cannot see the client's capabilities (no `initialize` in the same session), so it uses rung 2: an ordinary result `CONSENT_REQUIRED` with `consent_url`. It arrives unchanged **through the Gateway and directly**.
  2. *Runtime stateful (`MCP_STATELESS=false`), Gateway with sessions:* called **directly**, the Runtime returns the real `-32042` with the consent URL. Called **through the Gateway**, the answer is a tool result with `isError` and the text `McpException - MCP invocation failed: URL elicitation required`: **the consent URL is lost**.
  3. *Same, plus response streaming on the Gateway:* the same loss.
  The Gateway documentation ("Use elicitation with your AgentCore gateway") says it forwards a `URLElicitationRequiredError` to the client; in these two configurations it does not (n = 1 call each, same behaviour in both).
- **Decision.** On AWS the server stays **stateless** and the diner's approval link travels as the ordinary `CONSENT_REQUIRED` result (rung 2 of D-016), which works through the Gateway for every client, including one that declares URL elicitation. `-32042` remains the rung for clients that talk to the server directly with a session (local profile, tests). Nothing stateful is deployed.
- **Why stateful is a trap on AWS:** with a session the server would raise `-32042` and the Gateway would turn it into an error without the link, so the diner would have no way to approve. The deployed configuration (no `MCP_STATELESS` variable, no gateway sessions, no streaming) is the tested one: the experiment was reverted and 17 of 17 Gateway and Runtime tests pass again. The switches stay in the CDK app, off by default (`RUNTIME_STATELESS=false`, `GATEWAY_SESSIONS=true`, `GATEWAY_STREAMING=true`), so the experiment can be repeated if AWS changes the behaviour.
- **Acceptance of P2-7:** "step-up works through the Gateway or the direct route is used": it works through the Gateway as rung 2 (`tests/aws/test_demo_flow.py`: Bob's approval flow).
- **Real model through the Gateway (same day, DeepSeek flash, 5 runs of one booking):** it booked the table every time with the Gateway's prefixed tool names (steps: search, availability, mandate status, hold, confirm; 25,097 to 32,263 tokens a run, about $0.005 each at the price in D-028). In 3 of 5 runs it first reused the hold's `idempotency_key` for `reservation_confirm`; the server refused it (`IDEMPOTENCY_CONFLICT`, a key cannot be shared by two tools) and the model recovered by itself. A sentence about unique keys was added to the assistant's instructions; afterwards 1 of 2 runs was clean. Small samples; no claim about reliability.

## D-049 – Gateway Policy G1-G4 as defence in depth: opt-in, deployed and measured on the second account (P2-6, 2026-10-01/02)
- **What.** One policy engine (`fairtable_engine`) and six Cedar policies in `infra/gateway/policies/*.cedar` (the file name is the policy name): G1 reads for any OAuth user, G2 writes need `username` and the `fairtable/book` scope, G3 one `forbid` per tool that has a `party_size` input (`availability_check`, `restaurant_search`, `waitlist_watch`), G4 writes only from `agent_tier == "verified"` (with the `hasTag` guard: an error in a `forbid` is skipped and the permit would win). The server runs the same rules (PEP-1) first; the Gateway repeats them and is never the only place.
- **Known gap, accepted.** `reservation_hold`, `reservation_confirm` and `reservation_manage` take a slot token or an id, not a party size, so a party above 10 on those tools is refused by the server only. The local scenario `write-party-of-11` is therefore expected as `allow` at the Gateway (`SERVER_SIDE_ONLY` in the test) and `deny` at the server.
- **Opt-in.** `GATEWAY_POLICY=LOG_ONLY|ENFORCE` in the CDK app; unset means no engine (the deployed stack does not change). Policies are created one at a time after the target (the service validates each statement against the gateway's tools), with `FAIL_ON_ANY_FINDINGS` so a statement the service's schema refuses fails the stack, and `enforcementMode` `ACTIVE`. The gateway role gains `AuthorizeAction`, `PartiallyAuthorizeActions` and `GetPolicyEngine` on its engine and `fairtable-gw-*` gateways only (without them every call is denied, documented).
- **Two deploys (found on the first try).** `CreatePolicy` returns before the service validates the statement, and CloudFormation does not wait for `ACTIVE`; a `forbid` validated while the `permit` for its tool was still being checked was refused (`Overly Restrictive`), and CloudFormation then hung for 19 minutes until the update was cancelled (clean rollback). So the permits (G1, G2) are created first (`GATEWAY_POLICY_STAGE=permits`), then the forbids (G3, G4); `aws_ctl.py up` does both when `GATEWAY_POLICY` is set. Friction log has the details.
- **Measured (second account, 2026-10-02).** All six statements accepted with `FAIL_ON_ANY_FINDINGS` (the approximate local schema was close enough). `LOG_ONLY` then `ENFORCE` through CloudFormation (about 70 s each). Under `ENFORCE`: a refused call is a **JSON-RPC error** `Tool Execution Denied ... [Policy evaluation denied due to <policy name>-<id>]` (not a tool result, so the server's `POLICY_DENIED` is no longer what a client sees for G2 to G4 on this route); `tools/list` shows the bot and the unverified agent only the four read tools; a party of 11 on `availability_check` is refused by its G3 policy; every legitimate flow (booking through the chat, Bob's step-up with the consent page, Alice's cancel) still passes: real-AWS tests 34 of 34 (see the devlog entry). `tests/aws/test_gateway_policy.py` has the five policy tests.
- **State left on the account:** the engine stays attached in `ENFORCE` until the teardown (D-044). Teardown: `aws_ctl.py` lists and removes the engine with the Gateway stack.
- **Limits of the evidence.** The service gives no way to read the Cedar schema it generates from the tools, so the local validation uses an approximation (`local.cedarschema`); the first real validation is the deploy itself. The shape of a refusal at the Gateway (JSON-RPC error or `isError`) is not documented and is to be measured.
- **Cost** (AgentCore pricing page, read raw on 2026-09-30): $0.000025 per authorisation request, no idle charge. A demo of a few hundred calls costs well under a cent.

## D-051 – Confirmation becomes 100 % voice; what the Alexa+ documentation says (2026-10-02)
Decided by the developer after the research below. Nothing is built yet; the build is plan task P3-10.
- **What the Alexa+ documentation says** (developer.amazon.com/docs/alexaplus/add-ons, read 2026-10-02; the lifecycle page was read raw, last updated 2026-07-10; the others through a fetch tool's summary, one source each):
  - The Alexa+ MCP client sends `initialize` with `protocolVersion 2025-03-26` and capabilities `{roots: {listChanged: true}}` only: **no `elicitation`**. The overview page says Alexa+ supports MCP 2025-11-25; the two pages disagree and the sample payload is the more specific one. The spec forbids a server to send an elicitation mode the client did not declare, so server-initiated elicitation (`-32042`, form mode) **cannot be relied on with Alexa+**. This closes the open point of D-014.
  - The session is the customer's Alexa conversation, not an MCP session id, over Streamable HTTP: a stateless server fits.
  - A tool result with `_meta.ui.resourceUri` (`ui://...`) gets a custom MCP App UI; without it Alexa+ renders the data itself. MCP Apps are therefore supported but optional; they stay out of scope (voice-first).
  - The add-on functional requirements (under "Certify") say, for devices without a screen: complete every critical flow by voice, at most 5 options, never refer to visual elements, read back the details and require an explicit "yes" before any commitment. Errors must carry no codes, tool names, JSON or internal ids and always a next step. Checkout (payments) is handled by Alexa+ itself with voice PIN and purchase confirmation; the pages only discuss payments.
- **Decision.**
  1. The approval page (phone) is **removed from the booking flow**. A booking outside the diner's standing permission, or with a fee, is confirmed by a **spoken yes** that the assistant relays; no link, no second device, no e-mail or SNS message (the written-confirmation requirement targets payments; dropped, developer).
  2. The server guards the relay instead of trusting it: `reservation_hold` returns the terms, the sentence to read back and a `terms_hash`; `reservation_confirm` must carry that hash (so it is about exactly those terms, fee included) and must arrive after a minimum pause since the read-back (so it cannot be issued in the same breath as the hold). A call that fails a guard is refused with a spoken next step ("read the details back and ask for a yes"); it books nothing. Caps (S1, S2), idempotency and the standing permission stay as they are.
  3. Every confirmation is stored with how it was given (`mandate` | `spoken`) in the same transaction as the booking, and the report counts spoken confirmations separately.
- **What this does not guarantee (stated, not hidden).** The server cannot hear the diner. A model that learns the hash, waits and calls `reservation_confirm` looks the same as a diner who said yes. The guards stop mistakes (forgetting to ask, asking too fast, confirming other terms than the ones read) and bound the damage with the caps; they do not stop a model that lies on purpose. The phone approval did stop that; giving it up is the developer's choice (voice-first, no manual step on a device without a screen).
- **What it replaces** (they stay in this file as history; the code is retired in P3-10): the `-32042` middleware and ladder (D-014, D-016), approvals, consent URL and the dev inbox (D-020), the hold lengthened for the approval window (D-022), the permission tick box on the approval page (D-033), `CONSENT_REQUIRED` as a link (D-047, D-048). The AWS profile gets simpler: nothing depends on `-32042` passing the Gateway.
- **Consequences for the evaluation.** A2 ("no step-up", D-027) is redefined as "confirm without the voice guards". Invariants I1 and I3 are restated for spoken confirmations (a booking outside the permission needs a confirmation that passed the guards); the safety grader reports `spoken` bookings as their own line. Red team RT5 becomes "a confirm without the read-back hash or too soon is refused". The 40 tasks keep their shape: `consent: approve | decline | ignore` now means the diner says yes, says no, or says nothing (the field may be renamed).
- **Open (decide in P3-10, ask first):** how a standing permission is created by voice (there is no ninth tool and the tick box is gone; today the data is seeded); the minimum pause (propose 3 s, measure with a real model); whether a booking with a fee needs a stricter voice step (for example the fee read back and a second yes); what remains of the owner console and of `web/`; whether the retired code is deleted or kept behind a flag.
- **Notes and the full comparison:** `docs/alexa-plus-addon-notes.md`.
- **Deliberate differences from the add-on requirements, to be written in `ARCHITECTURE.md`:** no written confirmation (e-mail, SNS); `modify` only reduces the party size; the standing permission lets in-permission bookings confirm without a spoken yes.

## D-055 – How the voice confirmation was built, and where it differs from the plan (P3-10, 2026-10-02)
Built after D-051, D-053 and D-054; plan `docs/plan-p3-10-voice-confirmation.md`, test map `docs/plan-p3-10-test-map.md`.
- **A signed read-back token, not a bare hash.** The plan said `terms_hash`. A plain SHA-256 of public terms is something a model could compute without any read-back. The token is `base64url(payload).HMAC-SHA256` (the slot-token pattern, `server/domain/readback.py`) and binds the kind (`confirm` | `cancel_fee`), the hold or reservation id, the user's `sub`, the hash of the terms (fee included) and the moment it was handed over. It is valid for 3 hours (a confirm; a Fair Drop winner holds for 2) or 15 minutes (a cancel). Same secret as the slot token (`SLOT_TOKEN_SECRET`), different payload shape.
- **No new storage.** The plan reused the approval records as a read-back record. The token carries everything, so the approval entity, its keys, mapper, repository methods and the `extend_hold` of D-022 are simply gone. A booking stores `confirmation = "spoken"` and `read_back_at` (when the token was handed over; empty when none fitted, which only happens when the guards are off); a cancelled reservation with a fee stores `cancel_read_back_at`.
- **Rules.** S5a (token missing, malformed, stale or for other terms, another user or another hold), S5b (pause since the token not yet passed: 3 s, 6 s with a fee), S5c (`user_confirmed` not true). They apply to `reservation_confirm` always and to `reservation_manage` only for a cancel that costs money (the caller sets `read_back_required`). S3 and S3b were deleted. A refusal after S5a carries a **fresh** token and the read-back sentence in `details`; after S5b or S5c it carries none (a new token would restart the pause and trap the assistant in early calls).
- **The engine has no `step_up` any more.** `DecisionKind.STEP_UP`, `@on_deny("step_up")`, `StepUpRequired`, the `-32042` middleware path and `server/tools/stepup.py` are removed; the pipeline treats any non-allow decision as a denial. Error codes `CONSENT_REQUIRED`, `CONSENT_DECLINED` and `FEE_APPLIES` are replaced by `CONFIRMATION_REQUIRED`.
- **Mandate and approvals removed everywhere:** domain (`Mandate`, `grant.py`, `mandate.py`), store, seed, the `mandate_status` tool (seven tools), the Gateway read policy and its schema, the consent and permissions pages of `web/`, `CONSENT_BASE_URL` (now `WEB_PUBLIC_URL`, only for the cookie), and the CDK environment variable of the Runtime.
- **Stateless by default** in every profile (`MCP_STATELESS` true unless set to false); hold lengths 10 minutes, 30 for a waitlist match (`MATCH_HOLD_TTL_S`), 2 hours for a Fair Drop winner (`DROP_HOLD_TTL_S`). The notices of the matcher and the dropper no longer say "ten minutes".
- **Invariants restated.** I1: every reservation has `confirmation = spoken` and a `read_back_at` not later than its creation. I3: a cancelled reservation with a fee has `cancel_read_back_at`. The harness adds a ground truth the server cannot have: a reservation although the simulated diner never said yes is a violation `I1`.
- **A2** is now "the real rules judged as if the voice facts were satisfied" (`NoVoiceGuardsPep2` re-judges with the facts forced to true, because a `forbid` hides a missing `permit` and turning S5 refusals into allows would also have let in an unverified agent; found by a unit test).
- **Evaluation.** Personas read the details back and wait for the diner; the simulated diner answers yes, no or nothing after 8 s on the test clock (longer than the 6 s pause); two new misbehaviours: `eager` (confirms in the same breath, claiming a yes) and `forgetful` (leaves the token out the first time). The 40 tasks were regenerated (HAPPY 12, NEG 8, ROB 8, ADV 12; 4 eager ADV tasks, 3 forgetful ROB tasks). Red team RT5 is "a confirm without the read-back of its own terms" (no token, and the token of another hold).
- **Measured once, mock model, k=1, all 40 tasks:** A1: 40 of 40 pass, 0 violations. A0: blocks 0 of 12 attacks, has 7 violations (4 eager, 3 forgetful). A2: blocks 8 of 12 attacks (the four eager ones get through), has the same 7 violations and pass@1 0.85. (A0 and A2 together: 80 trials, 56 passed, 24 failed.) These validate the harness; the report with k > 1 is P3-2.
- **Differences from the plan, stated:** steps 2 to 5 were done together rather than green after each (a renamed context field breaks every caller at once); the whole local suite is the gate; the AWS redeploy (step 8) and the real-model check are not done.

## D-059 – Short identifiers: `offer_id` and the eleven-character read-back code (2026-10-02; the developer chose option A)
- **Why.** On Amazon Nova 2 Sonic the 295-character signed `slot_token` came back with one character changed (index 162), nine times in a row, and every hold was refused (`bad_signature`). With a stub server and the same model, an 8-character offer id, a 32-character hold id and an 11-character read-back code were each copied correctly in 3 of 3 booked conversations. Amazon's requirement 13 also asks for stable identifiers that one tool returns and the next accepts.
- **Offers are stored.** `availability_check` writes one item per slot shown (at most five, one transaction, `attribute_not_exists` so an id is never overwritten): `OFFER#<id>` with the restaurant, day, slot, party size, slot version, the user and `expires_at` (15 minutes, `OFFER_TTL_S`), plus a `ttl` attribute that DynamoDB uses to delete old items (turned on in the CDK table; the expiry is still checked on every read). `reservation_hold(offer_id, idempotency_key)` reads it, checks the user and the expiry, and the rest is as before (the slot version still decides whether the slot is free). Codes are 8 characters of Crockford's base32 without i, l, o, u (40 bits); capitals, spaces, dashes and the look-alikes o/0, i/l/1 are read as the code.
- **Read-back code.** 11 characters: the moment of issue in half seconds, rounded up (3 characters, modulo 4.5 hours) plus 40 bits of an HMAC over the kind, the subject, the user, the terms and that moment (8 characters). Nothing is stored; the moment is recovered from the three characters, so the pause and the age work as before. Rounding up means a pause can be up to half a second longer than asked, never shorter. Invariant I1 allows one second between the read-back and the creation.
- **Error codes** `INVALID_SLOT_TOKEN` and `SLOT_TOKEN_EXPIRED` became `INVALID_OFFER` and `OFFER_EXPIRED`; the parameter `slot_token` became `offer_id`. `hold_id` (32 hexadecimal characters) is unchanged: it was copied correctly. The environment variable `SLOT_TOKEN_SECRET` keeps its name (it signs the read-back codes now).
- **`availability_check` still has `readOnlyHint: true`** although it writes offers and rate counters: they are disposable bookkeeping, not state a diner would call a change. Revisit if Alexa+ is found to treat it differently.
- **Limits.** One experiment of three conversations on one model; the end-to-end voice test through the Gateway is the real check (devlog). A model could still mistype an eight-character code; the answer is a refusal with a next step (look again), not a booking.

## D-061 – `restaurant_search` forgives a misheard name and says how sure it is (2026-10-02; the developer's request)
- **Why.** The old search needed every word of the query to appear in the restaurant's text, so "Luna Tratoria" found nothing. On a voice call the name comes from speech-to-text and is often a little wrong.
- **What.** `server/domain/venue_match.py` (pure, standard library only, no model, so the tools stay deterministic): normalise (case, accents, punctuation, filler words such as "the" or "please"), then classify every restaurant as `exact` (every query word is a word of its name, so "Luna" or "grill" is exact), `topic` (every word is a word of the name, cuisine, city or description, so "italian" or "riverside"), or `close` (spelling or sound like the name: similarity of the whole string and of the words, also on a rough sound key where c/k/q, ph/f, double letters and h agree; kept from 0.72 up). Order: exact, topic, then close by score. A found name is never mixed with look-alikes. Nothing unrelated matches ("Burger Palace", "pizza").
- **Output.** Every restaurant has `match` (`exact`, `topic` or `close`); close ones also `match_score` (0.72 to 0.99, never 1.0). The result has `confirm_name`: true when the best result is only close. Then the `spoken_summary` is a question, never a statement: "I did not find that exact name. The closest is X. Is that the restaurant you mean?" (or "The closest are X and Y. Which one do you mean?" when two scores are within 0.08), and `next_step` says to wait for a yes before `availability_check` and to search again after a no. The tool description and the server instructions say the same to the model. The score is for the model; it is never in the spoken text.
- **Limits.** The thresholds were chosen on three restaurants and about forty hand-made queries (unit tests); with many restaurants the false-positive rate will differ. The read-back is a model's behaviour that the server asks for but cannot force: the server cannot hear the diner (as with the booking yes). The booking itself is still guarded by the hold / read-back / spoken yes, so a wrong restaurant that slips through is read back again in the hold's sentence. Words that have no stable spelling (names in other languages) are matched by the same letters only.
- **Behaviour change.** Before, "sakura count" (part of a word) matched by substring; now only whole words count for `exact` and `topic`, and such a query is `close`.

## D-062 – A clock for the lazy routines, an S3 copy of the audit and KMS for the seed (P3-15, 2026-10-02; the developer's request)
- **What.** On the AWS profile one Lambda, `FairTableWorkers` (`workers/handler.py`, the Runtime's zip, arm64, Python 3.12, 512 MB, 55 s), is started by an EventBridge Scheduler schedule `rate(1 minute)`. It calls `server/workers.run_once`: `sweep_holds` (every expired hold of the next 15 days is released with the existing `lifecycle.release_expired`; the freed table goes to the waiting diners through the same hook the server uses, so they get their notice without any request) and `allocate_due_drops` (every Fair Drop whose time has come is drawn with the existing `dropper.maybe_allocate`). The bucket `fairtable-audit-<account>-<region>` (DataStack; private, encrypted, TLS only) gets `drops/<drop_id>.json` after each draw (`server/audit_sink.py`, best effort: DynamoDB stays the source of truth). `SEED_PROVIDER=kms` makes the seed script draw the secret seed of each drop with KMS `GenerateRandom` (no key to manage).
- **The lazy design stays.** Nothing depends on the clock: the local profile runs without it, and the tools still release, match and draw on a request. The routines are idempotent with conditional writes, so the clock and a request may run at once (tests: `tests/integration/test_workers.py`).
- **Left out on purpose.** DynamoDB Streams: the schedule finds everything a stream would announce, and TTL is never used for business logic. Reserved concurrency for the Lambda: the account's Lambda limit is 10, and a reservation must leave 10 unreserved. A schedule that fires "at each drop time": the first run after the time draws it (one minute at most).
- **Price** (official price files, us-east-1, 2026-10-02): Scheduler $1.00 per million invocations after 14 million free a month; Lambda arm64 $0.20 per million requests and $0.0000133334 per GB-second after the free tier; KMS $0.03 per 10,000 requests after 20,000 free a month; S3 $0.023 per GB-month. 43,200 invocations a month are inside the free tiers; DynamoDB on demand adds a few tens of thousands of small reads a month. Everything is tagged `project=fairtable`, removed by `aws_ctl.py down` (the bucket empties itself first), and can be removed one stack at a time.
- **Cost of the sweep.** Each tick reads the hold index of every restaurant for 15 days (45 queries). Fine for three restaurants; a real service would keep an index of the holds that are still open.
