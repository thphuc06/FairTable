# Alexa+ add-ons: what the official documentation says, and how FairTable compares

Observations from the official Alexa+ for Builders documentation, read on 2026-10-02 for decisions D-051, D-052 and D-056 and plan task P3-9. The hackathon gives no Alexa+ tooling (D-001), and nothing here is a hackathon rule (`docs/hackathon-rules.md`): these pages are the best available description of what a good Alexa+ add-on is, so they feed the Design criterion. FairTable has **not** been tested with a real Alexa+ client and cannot be (nobody outside Amazon can); everything below is a comparison with the documentation plus our own tests.

**How each page was read.** *Raw* = the page's HTML was downloaded with curl and its text read in full (2026-10-02, pages "last updated" 2026-07-10 to 2026-07-21). *Summary* = a fetch tool summarised the page; treat it as one source.

## 1. Surfaces
- One integration reaches Alexa+ on capable Echo, Echo Show and Fire TV devices, the Alexa app and Alexa.com. The platform adapts rendering to the surface. Echo Dot is the voice-only example, and the lowest-capability device the testers use first.
- Requirements are scoped by device type: group 9 *Voice-Only Experience* applies to add-ons on devices without a screen; groups 10 and 11 to display devices.

## 2. The MCP client
- `initialize` request: `protocolVersion "2025-03-26"`, `capabilities {"roots": {"listChanged": true}}`, `clientInfo {"name": "Alexa+ MCP Client", "version": "1.0.0"}`. Expected response: `serverInfo` and `capabilities {"tools": {}, "resources": {}}`. **No `elicitation`.** (The overview page says 2025-11-25; the lifecycle page's sample says 2025-03-26: the two disagree. Our server answers with the client's version either way.)
- Transport: Streamable HTTP. The session is "based on the customer's previous conversations with Alexa+ rather than an explicit identifier", so a stateless server fits (stateless is the default in every profile since P3-10).
- A tool result carries `structuredContent` and `content` (text); with `_meta.ui.resourceUri` Alexa+ renders the add-on's own MCP App UI, otherwise it renders the data itself.
- Tool signatures and descriptions are **locked after publication** (certify page): the names and parameters should be final before any real submission.

## 3. Authentication and account linking (raw pages)
- **Two tiers.** Tier 1 is a service-level token (`client_credentials`, scope `mcp:service`) used for `initialize`, `tools/list`, catalog browsing and health checks. Tier 2 is a user-level token (`authorization_code` + PKCE S256) used when a user-specific tool is called. Both arrive as `Authorization: Bearer`. Not supported: dynamic client registration, OIDC, step-up authorization, `WWW-Authenticate` headers in 401 answers.
- **The server's duties** (account-linking page): host `/.well-known/oauth-protected-resource` on the MCP server (`resource`, `authorization_servers` (only the first is used), `scopes_supported`); **return HTTP 401 or 403 when a tool is called without a valid token** (Alexa+ then starts account linking itself: QR code on screens, a push notification to the app on headless devices); scope all data to the current token; the authorization server must support PKCE S256 and issue refresh tokens. Redeploy the add-on when authorization metadata changes.
- **Certification principle 1:** "The customer completes their task with Alexa. No redirects to websites or apps are necessary to finish the action." and the testers' watch-out "handoffs to a phone, app, or website for tasks that could resolve within the conversation". This is why the phone step-up was removed (D-051).
- **Friction:** "customers can browse, search, and view results without signing in or linking accounts, if possible"; account linking only when an action needs it.

## 5. Deliberate differences (to be written in `ARCHITECTURE.md`)
1. **No written confirmation** (e-mail, SNS): the requirement sits under "Creating & Completing"; the developer removed e-mail on purpose (D-051).
2. **`modify` only reduces the party size** (D-020). Changing the day or time means cancelling and booking again, which the assistant can do in one conversation. This is weaker than the page's example ("Change it to Sunday").
3. **No duplicate-booking detection** for the same restaurant and day. Retried requests are safe (idempotency), and rule S1 limits the open holds per restaurant, but a diner can hold or book two tables on the same day. Adding a rule is a behaviour change (decision needed).
4. The server cannot hear the diner: a spoken yes is relayed by the assistant and guarded by the server, not proven (D-051). The phone approval that did prove it was removed on purpose.
5. No custom MCP App UI (supported by Alexa+, optional; the product is voice-first).
6. **Token source.** Alexa+ sends the user's access token as `Authorization: Bearer`. The FairTable server reads the user's token only from `x-ft-user-token` and deliberately ignores `Authorization` (a test pins it): on AWS the Gateway checks the bearer token (Cognito) and its interceptor copies it, so a client cannot forge the header. A server run directly behind Alexa+ would need a proxy that does the same, or a change to accept `Authorization` (not built, decision needed).
7. **Not built, because there is no Alexa+ to try them with:** the `/.well-known/oauth-protected-resource` document, an authorization server for Alexa+ (the dev issuer and Cognito are not configured for Alexa's redirect URIs), the service-level (`mcp:service`) token flow, and a 401/403 for a valid service token calling a write tool (today it is a rule refusal, G2, so Alexa+ would not start account linking). Measured on 2026-10-02 against the deployed Runtime (called directly, with SigV4): a `tools/call` with no token, a token that is not ours or an ID token ends as an **HTTP error** at the caller, so the Runtime passes the server's 401 on (`tests/aws/test_runtime_smoke.py`). Behind the Gateway the Gateway checks the bearer token first and answers 401 or 403 itself; whether it would pass on a 401 from the server was not measured (the Gateway never lets such a call through).

## 6. Other observations, not explored
- The documentation navigation lists a **Category SDK** with SPIs, among them *Restaurant Reservation SPI*, a different integration path from the MCP toolkit and out of scope for this hackathon track, but it shows where restaurant booking sits in Alexa+. There is a sample end-to-end test script for restaurant reservations (not read).
- Design guide pages: inline mode for confirmations, summaries and single decisions; commit screens must not truncate details. Relevant only if a custom UI is ever added.
- Testing guidance: complete the whole experience by voice only; test on Echo Show (primary), the Alexa app, Alexa.com and a voice-only device; mid-flow corrections ("Actually, make that 6 people") and partial requests are tested explicitly. The local MCP Inspector is the recommended first test of the server alone.
- Policy requirements: no placeholder or test data in a store listing, a privacy policy URL, no unbounded open text fields unrelated to the purpose (FairTable's only free text is the restaurant search query).

## 7. Probe of our server with the Alexa+ client's requests (2026-10-02)
`tests/integration/test_alexa_client_compat.py` sends the payloads of the lifecycle page to the real server over HTTP, with no database. Measured:
- **Stateless mode (the default everywhere):** `initialize` with `protocolVersion 2025-03-26`, `roots` only and a string id is answered with protocol **2025-03-26** and `tools` and `resources` among the capabilities (it also lists `prompts`, `logging`, `tasks` and `extensions`, which the Alexa+ sample does not mention); `notifications/initialized` gives 202; `tools/list` and `tools/call` work with **no session id**; a tool result carries `structuredContent`, a text `content` and `isError`; the `MCP-Protocol-Version: 2025-03-26` header is accepted, an unknown one gets 400 naming the supported versions; every tool has an `inputSchema` and a description.
- **Stateful mode (`MCP_STATELESS=false`):** every call after `initialize` without a session id gets **400 "Missing session ID"**. Amazon's page shows no session id on follow-up calls, so it is not used (kept as a test).
- **Tool call without a token:** HTTP **401** with `{"error": "unauthorized", "message": "Access token required to use this tool."}` (the body Amazon's page shows). Before P3-9 it was HTTP 200 with a tool-level error, which Alexa+ would not read as "start linking".
- **Limits of this probe:** it uses the sample payloads only. It does not show what else the real client sends.
